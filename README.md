# Assignment Submission Portal

A simple assignment submission portal for a course. Students enter their name, registration number, assignment title and submission URL. Valid submissions are saved and displayed; invalid ones are rejected with validation messages.

## Features

- **Submission portal**: `POST /api/submissions` validates the required fields (name, registration number, assignment title) and the submission URL (must be a valid `http`/`https` URL). Valid submissions are persisted to `submissions.json` and returned through `GET /api/submissions`. The static frontend in `client/index.html` provides the student form and shows the saved submissions.
- **Automated tests**: Jest + Supertest covering submission validation and persistence.
- **CI pipeline**: GitHub Actions workflow (`.github/workflows/ci.yml`) runs the tests on every push, delivers the generated test report to the local receiver and emails it.
- **Local report receiver**: `server/reportReceiver.js` listens on `http://localhost:8787` and saves received test reports as `test-report.json`.

## Repository layout

```
client/index.html            Static frontend for the submission portal
server/index.js              Express app with submission API
server/reportReceiver.js     Local HTTP receiver for test reports
server/__tests__/            Jest test suite
scripts/send-report.js       Builds the test report JSON and POSTs it to the receiver
scripts/send-report-email.js Sends the test report by email (Resend)
.github/workflows/ci.yml     GitHub Actions CI pipeline (tests, report, deploy)
test-report.json             Generated by the local receiver (latest test report)
submissions.json             Generated runtime store for valid submissions
```

## Setup and run

```bash
npm install
npm start        # starts the portal on http://localhost:3000
npm run start:receiver   # starts the local test report receiver on http://localhost:8787
npm test         # runs the automated tests
```

## Automated tests

The pipeline executes the following test cases (see `server/__tests__/submissions.test.js`):

1. **Complete details and a valid submission URL** -> the submission is saved and appears in the submission list.
2. **Missing registration number** -> the submission is rejected with a validation message.
3. **Invalid submission URL** -> the submission is rejected and is not saved.

A failed test causes the CI test stage to fail.

## Continuous integration and local report receiver

The GitHub Actions workflow (`.github/workflows/ci.yml`) triggers on every push to any branch (and manually via `workflow_dispatch`).

After `npm test -- --json > test-results.json` completes, the workflow:

1. Builds a test report containing repository name, branch, commit SHA, pipeline run id, execution timestamp, per-test results (name, result, failure message) and total/passed/failed counts with overall status.
2. POSTs the report to the local receiver via the `LOCAL_REPORT_RECEIVER_URL` secret (an ngrok/localtunnel public tunnel that forwards to the receiver running on the instructor's machine).
3. Sends the report by email via the Resend API (secrets: `RESEND_API_KEY`, `REPORT_EMAIL_FROM`, `REPORT_EMAIL_TO`).

The local receiver writes the report to `test-report.json` on the instructor's computer.

### Running the receiver and tunnel locally

```bash
npm run start:receiver     # terminal 1: http://localhost:8787
npx localtunnel --port 8787   # terminal 2: gives a public URL forwarding to localhost:8787
```

Set the repository secret `LOCAL_REPORT_RECEIVER_URL` to the tunnel URL (for example `https://pretty-rats-post.loca.lt`) so the GitHub runner can reach the local receiver.

## Deployment (GitHub Pages frontend + hosted API backend)

The portal has two parts, and they must be deployed separately:

- **Frontend**: static `client/index.html` published to **GitHub Pages** via the `deploy` job in the CI workflow (Settings -> Pages -> Source: GitHub Actions, push to `main` with passing tests).
- **Backend**: the Express API (`server/index.js`) with `POST /api/submissions` and `GET /api/submissions`. GitHub Pages is static hosting only and can never serve API POSTs, which is why submissions used to fail with `405 Method Not Allowed`.

The backend is configured for deployment on [Render](https://render.com) via `render.yaml` (free tier). After pushing this change:

1. Push to `main` (or trigger a Render deploy from the repo blueprint).
2. The API is live at `https://hoodclock-assignment-portal-api.onrender.com`.
3. The frontend in `client/index.html` calls that backend base URL (`window.SUBMISSIONS_API_BASE_URL` can override it, e.g. set it to `http://localhost:3000` for local development).

The frontend form therefore posts to `<API_BASE_URL>/api/submissions` instead of the relative `/api/submissions` that GitHub Pages could not handle.

## Email report (bonus)

The workflow sends the test report by email after every run (passing or failing) using the Resend API. Configure the repository secrets:

- `RESEND_API_KEY` - Resend API key
- `REPORT_EMAIL_FROM` - sender address (use `onboarding@resend.dev` for testing, or an address on a verified Resend domain)
- `REPORT_EMAIL_TO` - recipient email address

## Demonstration summary

1. Push a revision with passing tests -> CI passes -> `test-report.json` contains the passing report.
2. Introduce a defect -> push again -> CI fails -> `test-report.json` contains the failing report.
3. Fix the defect -> push again -> CI passes -> `test-report.json` contains the passing report again.
